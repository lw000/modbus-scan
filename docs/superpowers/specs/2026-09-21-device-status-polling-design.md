# 设备详情页状态轮询设计

## 目标

设备详情页不再周期调用 `GET /api/v1/devices/:id`，也不再通过 HTTP 轮询点位实时值。页面首次加载设备静态信息后，仅轮询已有的设备状态接口，以更新运行状态。

## 页面数据流

页面首次打开时调用 `GET /api/v1/devices/:id`，获取设备名称、地址、端口、Slave ID 和初始运行状态；同时按现有逻辑加载点位列表。

页面可见期间每两秒调用 `GET /api/v1/devices/:id/status`。轮询结果只更新状态徽标、配置待生效标记和最后错误，不重复渲染设备静态信息或点位列表。页面隐藏期间不发起状态轮询。

启动、停止或重启操作成功后，页面继续执行一次完整刷新，使设备信息、运行状态和点位配置保持一致。点位实时值继续由现有 WebSocket 订阅提供。

## 前端结构

设备摘要渲染拆分为静态设备信息和动态运行状态两部分：

- 首次加载函数请求完整设备详情，并渲染静态信息与运行状态。
- 状态轮询函数请求 `/status`，并只更新动态状态区域。
- 周期定时器调用状态轮询函数，不再调用完整设备详情函数。

不修改后端接口、数据库、采集运行时或 WebSocket 协议。

## 错误处理

状态请求失败时沿用现有 `showError` 行为。`busy` 继续防止完整刷新重叠；状态轮询保持单次轻量请求，不触发点位列表加载。

## 测试

更新嵌入式 Web 资源测试，验证设备详情脚本：

- 包含对 `/api/v1/devices/${id}/status` 的请求。
- 周期定时器调用状态加载函数。
- 周期定时器不再调用完整设备详情加载函数。
- 点位实时值仍使用 WebSocket，不恢复 `/values` 轮询。

运行相关 Web 资源测试和完整 Go 测试，确认嵌入资源与现有后端行为未被破坏。
