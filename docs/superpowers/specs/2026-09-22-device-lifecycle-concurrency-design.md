# 设备生命周期并发控制设计

## 背景与目标

多个浏览器页面可能同时对同一设备发起启动、停止或重启请求。当前运行时使用每设备 `sync.Mutex` 串行执行这些操作，后到请求会等待前一请求结束。这可以保护运行时状态，但页面会长时间等待，并可能在等待后执行已经过时的用户意图。

本次改为每设备单操作语义：同一设备已有启动、停止或重启操作时，新的外部生命周期请求立即失败，并明确提示“设备正在操作，请稍后重试”。不同设备仍可并发操作。

## 方案选择

采用每设备非阻塞互斥。外部生命周期方法使用 Go 1.21 提供的 `sync.Mutex.TryLock` 获取现有 `deviceRuntime.opMu`；获取失败时返回稳定的 sentinel error。该方案沿用现有运行时边界，不新增队列、后台任务或数据库锁。

不采用以下方案：

- 原子状态机：能够表达更多操作阶段，但会重复现有运行状态和互斥职责，增加状态一致性风险。
- 操作队列：适合接受并依次执行所有命令，与“后续请求立即拒绝”的需求相反。

本设计仅保证单个 `modbus-scan` 服务进程内的并发控制。当前应用部署模型是单个 Windows 服务进程，因此不引入跨进程分布式锁。

## 后端设计

### 操作互斥

`runtime` 包新增导出的 sentinel error `ErrDeviceBusy`。`Manager.Start`、`Manager.Stop` 和 `Manager.Restart` 按以下顺序执行：

1. 获取对应设备的 `deviceRuntime`。
2. 调用 `opMu.TryLock()`。
3. 获取失败时立即返回 `ErrDeviceBusy`，不得读写数据库、runner、启用状态或运行状态。
4. 获取成功后设置当前操作类型，并用 `defer` 清理操作类型和释放锁。
5. 执行原有生命周期逻辑。

设备间使用独立的 `deviceRuntime`，因此设备 A 的操作不会阻塞设备 B。

### 内部生命周期

外部 HTTP 操作和服务自身生命周期采用不同等待策略：

- `Start`、`Stop`、`Restart` 面向交互请求，使用非阻塞抢锁。
- `StartEnabled` 在 HTTP 服务对外提供请求前运行，继续使用阻塞锁。
- `StopAll` 用于进程优雅退出，必须等待正在执行的设备操作完成后再停止 runner，继续使用阻塞锁，不能因 `ErrDeviceBusy` 跳过设备。

这样既满足页面快速反馈，也保证服务关闭不会遗留采集任务。

### 状态快照

`Snapshot` 新增可选字段：

```json
{"operation":"restart"}
```

`operation` 的有效值为 `start`、`stop`、`restart`，空字符串表示当前没有生命周期操作。该字段在持有设备状态锁时读写，并在操作返回的所有路径上通过 `defer` 清空。

运行状态 `state` 继续表示 collector 状态，例如 `starting`、`online`、`stopping` 和 `stopped`；`operation` 表示 API 操作是否仍占用互斥锁。两者职责不同，不能仅依赖 `state` 判断设备是否忙碌，因为重启的停止与重新启动之间可能短暂出现 `stopped`。

## HTTP 契约

HTTP 错误映射识别 `runtime.ErrDeviceBusy`，返回：

- 状态码：`409 Conflict`
- 错误码：`device_busy`
- 消息：`设备正在操作，请稍后重试`

响应结构沿用现有错误 envelope：

```json
{
  "error": {
    "code": "device_busy",
    "message": "设备正在操作，请稍后重试"
  }
}
```

其他存储冲突继续使用现有通用 `conflict` 错误，不与设备忙碌错误混用。

## 前端行为

设备列表页和设备详情页使用快照中的 `operation` 判断是否正在执行生命周期操作：

- `operation` 非空时禁用该设备的启动、停止和重启按钮。
- 操作发起页面在请求开始时立即禁用该设备全部生命周期按钮，而不是只禁用被点击按钮。
- 请求完成后立即刷新设备状态；定时轮询继续同步其他页面的状态。
- 收到 `device_busy` 时展示服务端消息并立即刷新状态，不自动重试，避免用户意图被延迟执行。
- 轮询只能改善交互，后端 `TryLock` 才是并发正确性的最终保障。

不新增跨页面浏览器锁。`localStorage`、`BroadcastChannel` 等浏览器机制无法覆盖不同浏览器或不同客户端，也不能替代服务端互斥。

## 错误处理与恢复

- 生命周期操作的成功和失败路径都必须清理 `operation` 并释放互斥锁。
- 抢锁失败只返回 `ErrDeviceBusy`，不包装成内部服务错误。
- 已获得锁后的存储、runner 创建、关闭或上下文错误继续保留原有错误链。
- 前端不根据中文消息判断错误类型，只依据稳定错误码 `device_busy`。

## 测试

### 运行时测试

- 同一设备已有操作时，第二个 `Start`、`Stop` 或 `Restart` 立即返回 `ErrDeviceBusy`。
- 忙碌请求不会修改 enabled 状态，不会创建或关闭 runner。
- 不同设备的生命周期操作可以同时执行。
- 操作成功和失败后均可再次获得操作锁。
- `Snapshot.Operation` 在操作期间可见，结束后为空。
- `StopAll` 等待正在执行的操作并最终停止所有 runner。

测试使用可控阻塞的 fake source、factory 或 runner 建立确定性的并发时序，不使用任意时长的 `time.Sleep`。

### HTTP 测试

- `ErrDeviceBusy` 映射为 HTTP 409、`device_busy` 和安全的中文提示。
- 其他未知错误仍映射为 HTTP 500。

### 前端资源测试

- 设备列表页和详情页都依据 `operation` 禁用全部生命周期按钮。
- `device_busy` 后触发状态刷新且不自动重试。

## 兼容性与文档

现有生命周期 URL、请求体和成功响应不变。`Snapshot.operation` 是向后兼容的新增 JSON 字段。README 的设备状态与生命周期 API 说明应补充 409 `device_busy` 契约和多页面并发行为。

## 完成标准

- 同一设备的并发外部生命周期请求不会排队，后到请求立即收到 409。
- 不同设备仍能并行操作。
- 所有页面能通过轮询观察操作状态并禁用生命周期按钮。
- 服务优雅退出仍会等待并停止全部设备。
- 新增并发、HTTP 和前端回归测试通过，且 `go test -race ./...`、`go test ./...`、`go vet ./...` 通过。
