# 项目设计开发技术文档

> 本文档用于指导 `modbus-scan` 项目的后续设计、开发、测试、评审和文档维护。
> `AI_DEV.md` 侧重业务规格与算法细节，`AI_DEV_RULE.md` / `AGENTS.md` 侧重通用 AI 协作规范；本文档侧重本项目的工程边界、开发约束和变更流程。

---

## 1. 项目定位

`modbus-scan` 是一个基于 Go 的 Modbus TCP 数据采集与本地 Web 管理服务，主要职责包括：

1. 从 TOML 加载 HTTP、SQLite 和日志等服务配置。
2. 使用 SQLite 持久化设备、点位、配置版本和启停状态。
3. 通过 Gin JSON API 和内嵌 HTML/CSS/JavaScript 页面管理配置。
4. 严格校验并事务化导入点位 CSV，也可导出兼容 CSV。
5. 将离散点位合并为 Modbus 批量读取块。
6. 周期性读取 Holding Register、Input Register、Coil Status、Input Status。
7. 将原始响应解析为带更新时间的内存实时值快照。
8. 通过运行时管理器控制设备启动、停止、重启和优雅退出。
9. 在通信异常时执行可取消的断线重连、熔断和低频探测恢复。

设备和点位不从 TOML 自动迁移。首次启动创建空数据库，由用户在页面手动配置。配置保存后不会自动影响运行实例，必须手动重启对应设备。

项目目标不是做通用 SCADA 平台，而是保持一个小而可靠的 Modbus 数据采集核心。新增能力应围绕采集、解析、点位配置、输出适配、运行可靠性和测试可验证性展开。

## 2. 开发原则

### 2.1 小核心、清边界

- `cmd/` 只负责命令行参数、启动编排、信号处理和依赖组装。
- `internal/config/` 只负责配置结构、配置解析、配置校验和读取块优化。
- `internal/collector/` 只负责 Modbus 连接、采集循环、数据解析、重连和写入。
- `internal/udm/` 只负责线程安全的数据读写快照，不承担采集、协议或持久化逻辑。
- 新增功能优先放入已有职责匹配的包；确实出现稳定的新职责时再新增 `internal/<name>/` 包。

### 2.2 标准库优先

除现有依赖外，新增第三方依赖必须满足以下条件：

- 标准库不能合理完成该功能。
- 依赖解决的是核心问题，而不是少量语法便利。
- 依赖维护活跃、API 稳定、许可证可接受。
- 新增依赖后必须同步 `go.mod`、`go.sum`，并运行相关测试。

### 2.3 显式配置、显式失败

设备地址、端口、从站 ID、扫描周期、字节序、点位模型等公共行为必须来自配置或代码中明确的默认值。不要在深层逻辑中引入隐式魔法值。

当前 CSV 加载策略为严格校验和原子导入：任意一行错误都会导致整次操作失败，不保存部分有效行。错误应包含行号、字段和原因。

## 3. 架构分层

### 3.1 启动层

入口文件：[cmd/modbus-scan/main.go](cmd/modbus-scan/main.go)

职责：

- 定义 CLI 参数。
- 根据 `-validate` 决定进入校验模式或采集模式。
- 加载服务配置并打开 SQLite。
- 组装运行时管理器、业务服务、Gin 路由和内嵌静态资源。
- 启动数据库中标记为启用的设备。
- 监听 SIGINT/SIGTERM 并触发 `context` 取消。

开发约束：

- 不在 `main.go` 中添加复杂业务逻辑。
- 不在 `main.go` 中直接解析 Modbus 响应或处理点位算法。
- 新增长期运行组件时必须接入同一个退出上下文，避免无法停止的 goroutine。

### 3.2 配置层

核心文件：

- [internal/appconfig/config.go](../internal/appconfig/config.go)
- [internal/config/point_config.go](../internal/config/point_config.go)
- [internal/pointcsv/csv.go](../internal/pointcsv/csv.go)

职责：

- TOML 服务配置加载、默认值和校验。
- CSV 点位配置严格解析、错误聚合和稳定导出。
- 点位数据类型、寄存器类型、位宽和寄存器占用规则。
- 按寄存器类型和地址合并读取块。

开发约束：

- 配置层不依赖采集器、UDM 或外部输出模块。
- 配置校验错误应包含字段名、行号、点位名和无效值，方便现场排查。
- 修改 CSV 字段、含义、默认值或校验规则时，必须同步示例 CSV、README、`AI_DEV.md` 和测试。
- 对外部输入的解析必须保守，禁止默默接受无法解释的枚举值。

### 3.3 采集层

核心文件：[internal/collector/collector.go](internal/collector/collector.go)

职责：

- 管理 Modbus TCP 连接。
- 按读取块执行 Modbus 批量读取。
- 解析线圈、离散输入、寄存器、位字段、多字节数值和字节序。
- 将解析后的设备原始值写入 UDM。
- 处理通信异常、重连、熔断和离线探测。
- 支持受控的反向写入。

开发约束：

- 采集层可以依赖 `config` 和 `udm`，但不应反向污染配置层。
- 所有网络 I/O 必须可观测，失败时保留操作上下文。
- 采集循环遇到通信错误时应避免继续发送本周期后续无效请求。
- 新增 goroutine 必须有退出机制，并响应项目主 `context`。
- 解析逻辑变更必须配套单元测试，尤其是位提取、字节序和有符号转换。

### 3.4 数据模型层

核心文件：[internal/udm/udm.go](internal/udm/udm.go)

职责：

- 用 `map[string]interface{}` 保存最新点位值。
- 提供线程安全的 `Update`、`Get`、`GetAll` 和 `LogAll`。

开发约束：

- UDM 只保存当前快照，不承担历史存储、报警判断、网络发布等职责。
- 需要导出、发布或持久化数据时，优先在 UDM 外新增适配层，通过 `GetAll` 获取快照。
- 不要把复杂业务状态塞入 `interface{}` 后再要求下游猜类型；新增输出协议时应在适配层做明确类型转换。

## 4. 核心数据流

```text
config.toml -> appconfig.Load -> logging.New -> store.Open
SQLite device + points -> runtime.Manager -> Collector -> UDM snapshot
Gin API + embedded web -> service -> store/runtime
```

开发时应优先保持该数据流单向清晰。不要让底层包回调 `main`，也不要让配置层直接访问采集连接。

## 5. 配置模型开发规则

### 5.1 设备配置

设备配置持久化在 SQLite，通过页面或 JSON API 修改。TOML 不再保存设备列表。新增字段时必须明确：

- 数据库列名和 JSON 字段名。
- 是否必填。
- 默认值。
- 有效范围。
- 是否影响连接、采集、解析或写入。
- 错误时是返回 error 还是使用默认值。

当前设备字段：

- `name`：设备名称，用于页面和日志标识。
- `enabled`：持久化的期望运行状态；新建设备默认停止。
- `address` / `port` / `slave_id`：Modbus TCP 连接参数。
- `byte_order`：多寄存器字节序，默认 `ABCD`。
- `timeout_sec`：通信超时，默认 5 秒。
- `scan_interval_ms`：采集周期，默认 2000 毫秒。

推荐模式：

```go
if cfg.Modbus.TimeoutSec <= 0 {
    cfg.Modbus.TimeoutSec = 5
}
```

不推荐在使用点临时判断默认值，因为会让行为分散，测试也更难覆盖。

### 5.2 点位配置

CSV 字段顺序属于公共接口。修改字段顺序或字段含义会影响已有配置文件，必须谨慎。

新增点位字段时需要同时完成：

1. 更新 `PointConfig`。
2. 更新 `LoadPointsFromCSV` 解析和校验。
3. 更新示例 CSV。
4. 更新 README 和 `AI_DEV.md`。
5. 添加成功、缺省、非法值、边界值测试。

### 5.3 校验策略

当前点位校验策略为严格校验：解析全部行并聚合错误，只要存在错误就不写入任何点位。Web 导入使用单一数据库事务，`-validate` 使用相同的解析器和规则。

## 6. 采集与解析开发规则

### 6.1 寄存器类型

当前支持：

| RegType | 读取方法 | 写入能力 | 上限 |
|---------|----------|----------|------|
| `HoldingReg` | `ReadHoldingRegisters` | 单寄存器写入 | 125 寄存器 |
| `InputReg` | `ReadInputRegisters` | 只读 | 125 寄存器 |
| `CoilStatus` | `ReadCoils` | 单线圈写入 | 2000 线圈 |
| `InputStatus` | `ReadDiscreteInputs` | 只读 | 2000 线圈 |

新增寄存器类型时，至少修改：

- `validRegTypes`
- `IsRegTypeBit`
- `OptimizeChunks` 的合并单位和上限
- `scanOnce` 的读取分支
- `WriteTag` 的写入限制
- README、`AI_DEV.md`、示例配置和测试

### 6.2 数据类型

当前支持：

- `Bool`
- `Int16`
- `UInt16`
- `Int32`
- `UInt32`
- `Float32`
- `Double`

新增数据类型时，至少修改：

- `validDataTypes`
- `TypeBitWidth`
- `PointConfig.GetRegisterCount`
- `parseAndUpdate` 的类型转换分支
- CSV 校验规则
- 字节序测试、边界值测试和 README

### 6.3 位提取

位编号约定是低位优先：

- bit0 表示最低位。
- `BitOffset` 使用右移实现。
- `BitLen` 表示提取位数。
- `BitOffset > 0 && BitLen == 0` 表示读取该偏移处 1 位。

变更该约定会影响所有点位语义，必须视为破坏性变更。

### 6.4 字节序

当前支持 `ABCD`、`DCBA`、`CDAB`、`BADC`。

约束：

- 2 字节单寄存器不做字节序转换。
- 4 字节和 8 字节按全局 `byte_order` 转换。
- 新增字节序必须给出明确的字节排列示例。

字节序逻辑是高风险区域，修改时必须添加覆盖 16、32、64 位的测试。

### 6.5 采集值

采集值语义：

```text
final = rawValue interpreted by byte order, bit extraction, and data type
```

约束：

- 完整宽度的 `Int16` / `Int32` 使用有符号转换。
- 位字段提取后的 `Int16` / `Int32` 按无符号字段处理。
- `Float32` / `Double` 不支持位提取。
- 不执行 Scale/Offset 工程值转换，CSV 中不再包含 `Scale` 和 `Offset` 字段。

## 7. 连接、重连与生命周期

### 7.1 连接管理

`ConnManager` 持有 Modbus handler、client、状态、重试计数和上下文。

状态：

- `StateOnline`
- `StateReconnecting`
- `StateOffline`

开发约束：

- 访问 handler/client 必须受锁保护。
- 状态和重连标志使用原子操作时，要避免与锁形成不清晰的交错。
- `Connect` 失败时必须返回错误，不应直接退出进程。
- 首次连接失败由启动层决定是否终止。

### 7.2 重连策略

当前策略：

- CAS 防并发重连。
- 指数退避：1s、2s、4s、8s、16s、30s，上限 30s。
- 连续失败 10 次后进入 Offline。
- Offline 后每 60 秒探测一次。

修改重连策略时应考虑：

- 是否会加重现场网络风暴。
- 是否会导致多个重连协程并发。
- 是否影响停机响应速度。
- 是否需要将参数配置化。

### 7.3 优雅退出

所有长期运行循环都应响应 `context.Context`。

当前已响应退出的组件：

- `ScanLoop`
- `startHeartbeatProbe`

`ReconnectWithBackoff` 使用可取消 timer；退避期间收到退出信号会立即返回，并有对应测试覆盖。

## 8. 反向写入开发规则

`WriteTag` 当前支持：

- `uint16` -> `HoldingReg`
- `int16` -> `HoldingReg`
- `int` -> `HoldingReg`，范围 0~65535
- `bool` -> `CoilStatus`

开发约束：

- 写入前必须检查点位存在。
- API 和 CSV 使用 `Writeable=1` 表示允许写入，进入采集器后转换为布尔权限并在写入前检查。
- 写入前必须检查设备在线。
- 不允许绕过点位配置直接按地址写入，除非新增明确的低层 API 并限制使用场景。
- 新增多寄存器写入、浮点写入或批量写入时，必须明确字节序、越界和部分失败语义。

## 9. 错误处理与日志

### 9.1 错误处理

- 跨层返回错误时使用 `fmt.Errorf("context: %w", err)`。
- 配置加载错误应返回给调用方，不在配置层 `os.Exit`。
- 采集周期内单个通信错误应触发重连并终止本周期剩余读取。
- 数据越界或点位解析异常应记录 WARN 并跳过该点位，避免单点位拖垮整个采集周期。

### 9.2 日志

当前日志前缀：

- `[INFO]`：启动、配置加载、连接成功、恢复成功。
- `[WARN]`：重连等待、未知类型、数据越界。
- `[ERROR]`：通信失败、熔断触发。

开发约束：

- 日志中不要输出密码、token、完整连接串或生产敏感数据。
- 高速采集路径中避免过量日志，尤其是每点位 debug 日志。
- 新增日志时应包含操作对象，例如地址、数量、点位名、配置文件路径。

## 10. 并发与资源管理

本项目当前主要并发点：

- 采集循环 goroutine。
- 重连 goroutine。
- 离线心跳探测 goroutine。
- UDM 的并发读写。

开发约束：

- 新增 goroutine 必须明确退出条件。
- 共享状态必须通过锁、原子操作或 channel 明确保护。
- 不要把 `context.Context` 存入新结构体，除非结构体本身就是生命周期管理组件。
- 文件、网络连接、ticker、timer 必须关闭或停止。
- 涉及并发状态修改时优先运行 `go test -race ./...`。

## 11. 测试策略

### 11.1 单元测试重点

配置层：

- TOML 默认值和非法值。
- CSV 合法行、非法行、重复 TagName、空文件。
- 每种 `RegType` 和 `DataType` 的校验规则。
- `OptimizeChunks` 的连续、断点、重叠、上限拆分。

采集层：

- 线圈位解析。
- 16/32/64 位寄存器解析。
- `ABCD`、`DCBA`、`CDAB`、`BADC` 字节序。
- `Int16` / `Int32` 有符号边界。
- `Float32` / `Double` 解析。
- 数据越界跳过。
- `WriteTag` 的只读、离线、类型不匹配、范围越界。

UDM：

- 更新、读取、快照隔离。
- 并发读写。

### 11.2 推荐验证命令

```powershell
go test ./...
go vet ./...
go test -race ./...
go build -o modbus-scan.exe ./cmd/modbus-scan
go run ./cmd/modbus-scan -validate -csv configs/points.csv
```

如果本地 Go build cache 权限异常导致命令尾部失败，应先修复本机缓存权限或设置可写的 `GOCACHE`，再判断业务测试是否通过。

### 11.3 测试数据

- 小型 CSV 测试数据可在测试中用 `t.TempDir()` 动态生成。
- 多场景固定样例可放入 `testdata/`。
- 不要提交真实设备地址、生产点位表、密钥或客户数据。

## 12. 常见变更流程

### 12.1 新增 CSV 字段

1. 更新 `PointConfig`。
2. 更新 CSV 解析和校验。
3. 更新示例 CSV。
4. 更新 README、`AI_DEV.md` 和本文档。
5. 添加字段缺失、非法值、默认值和兼容性测试。
6. 运行 `go test ./...` 和 `-validate`。

### 12.2 新增数据类型

1. 更新有效类型集合和位宽。
2. 更新寄存器占用计算。
3. 更新解析转换逻辑。
4. 更新位提取限制。
5. 添加字节序、边界值和原始值解析测试。
6. 更新文档和示例。

### 12.3 新增输出适配

输出适配包括 HTTP、MQTT、文件、数据库、消息队列等。

推荐做法：

- 新增 `internal/output/` 或更具体的包名。
- 通过 `UDM.GetAll()` 获取快照。
- 输出失败不应阻塞采集主循环太久。
- 外部 I/O 必须支持 context、超时和错误日志。
- 不要把输出协议逻辑放入 `udm` 或 `config`。

### 12.4 新增运行参数

1. 在 `main.go` 定义 flag。
2. 确定默认值和兼容性。
3. 必要时传入配置结构或构造函数。
4. 更新 README 命令示例。
5. 添加启动或配置测试。

## 14. 当前已知风险

### 14.1 无内建认证

HTTP 服务没有身份认证、权限控制和 TLS。默认应仅监听本机；监听其他接口前，部署环境必须提供访问控制和传输加密。

### 14.2 实时数据不持久化

点位实时值、更新时间和最近运行错误保存在内存，服务重启后不会保留历史。

### 14.3 浏览器自动化覆盖有限

API 和静态资源已有 Go 测试，但页面交互仍缺少独立浏览器端自动化测试。

### 14.4 容量需要现场验证

大量设备、高密度点位和较短扫描周期下的 CPU、内存、SQLite 写入和网络负载需要按实际部署规模压测。

### 14.5 本机构建产物

根目录可能存在旧的 `modbus-scan.exe`。新的二进制、数据库、日志、缓存、覆盖率文件或临时报告不得提交。

## 15. 开发前检查清单

开始改代码前：

# 实时值订阅补充

- WebSocket 端点：`GET /api/v1/ws`。
- 订阅消息：`{"action":"subscribe","device_id":1,"tags":["TagA"]}`。
- 取消订阅：`{"action":"unsubscribe","device_id":1,"tags":["TagA"]}`。
- 值消息包含 `type=value`、`device_id`、`tag_name`、`value` 和 `updated_at`。
- 每个连接最多订阅 500 个设备/位号组合，服务端按组合精确路由，不保存曲线历史。
- 批量删除接口 `DELETE /api/v1/devices/:id/points` 在事务中校验归属并删除 1 到 500 个点位，设备配置版本只递增一次。
